# L-109 파일 직접 전달 배포의 두 가지 함정

**상황/증상:** 정적 페이지(HTML 1개와 썸네일 PNG 약 300KB)를 연동 도구로 재배포하려 했다. 도구는 파일 내용을 요청 본문에 직접 실어야 했다.

**함정 1, 큰 이진 파일:** 이미지를 base64로 옮겨 적으면 분량이 크고(압축해도 수만 토큰) 한 글자만 틀려도 깨진다. 이미지를 공개 저장소에 올리고 페이지의 이미지 주소가 그 raw 주소를 가리키게 했다. 배포는 작은 HTML만 보낸다. 부작용: 기존 이미지 경로가 사라져 옛 주소만 아는 곳은 옛 이미지가 남을 수 있다.

**함정 2, 첫 배포 실패(확인):** 상태 `ERROR`, 설치 명령이 종료 코드 254로 실패했다. `package.json`이 없는데 프로젝트 기본 설치 명령이 돌았다. 이 배포에만 설치·빌드 명령을 건너뛰기(`echo skip`)로, 출력 폴더를 `.`로 지정해 재배포하니 정상 배포됐다.

**일반화:** 파일 직접 전달 배포는 ① 이진 파일을 인라인으로 보내지 말고 이미 호스팅되는 주소를 쓰고, ② 빌드가 없는 정적 페이지는 설치·빌드 단계를 명시적으로 건너뛰며, ③ 배포 후 상태와 라이브 응답을 직접 확인한다(요청 성공이 배포 성공은 아니다).

**근거:** 실패 배포의 오류 메시지, 성공 배포 상태, 라이브 응답(200, 새 문구와 이미지 주소)을 직접 확인.
