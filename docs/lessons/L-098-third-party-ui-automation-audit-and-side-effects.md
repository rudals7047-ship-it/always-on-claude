# L-098 메신저 자동화 도입 전 점검: 감사·부작용·권한

**상황/증상:** 상시 비서에 카카오톡을 검토 대상으로 넣고 싶다. 공개 도구(맥 앱의 접근성 트리를 읽는 CLI, MIT)가 있고, 개발자는 대화 DB·프로세스 메모리·네트워크를 건드리는 방식이 실제로 이용 제한을 받았다고 설명한다(영상 설명란, 저장소 README). 설치를 시도하자 자동 권한 검사가 설치·빌드를 거부했다.

**원인/판단 근거:**
1. [확인] 소스(약 5천 줄, 맥 쪽은 Python 두 파일과 Swift 세 파일)에는 네트워크 호출·DB 접근·base64 외부 전송이 없었다. 하는 일은 Swift 컴파일과 결과 JSON 해석이다.
2. [확인] 대화를 읽으려면 방을 열어야 하고, 닫혀 있던 방을 열면 상대에게 읽음으로 표시될 수 있다(README 명시). 목록 조회(방 이름·미리보기)는 방을 열지 않는다.
3. [확인] 제3자 코드를 내려받아 빌드하고 접근성 권한을 주는 일은 보안 경계를 넓히는 행동이라 자동 검사가 막았다. 우회하지 않고 사용자 결정으로 올린다.
4. [미확인] 영상 본문(자막을 받지 못함), 약관상 제재 가능성(개발자가 0%가 아니라고 밝힘).

**해결/방법:**
- 설치 전에 소스를 먼저 감사한다(네트워크·실행·민감 API grep, 의존성 수 확인). 의존성은 필요한 기능만(읽기 브리지, 전송 브리지는 빌드하지 않음).
- 부작용을 먼저 적는다: 기본 동작은 방 목록·미리보기까지만, 안 읽은 방은 열지 않는다. 본문 읽기는 이미 읽은 방이나 사용자가 요청한 방에 한한다.
- 같은 작업의 안전한 절반(iMessage 읽기 전용 스크립트, 검토 스킬)은 먼저 끝내고, 막힌 절반은 이유와 선택지를 사용자에게 넘긴다.
- 기록 규칙: 대화 원문은 저장하지 않고 일정·사용자 이해에 도움이 되는 사실만 요약한다. 인증번호·계좌 같은 식별 정보는 쓰지 않는다.

**일반화:** "공식 앱의 접근성 인터페이스를 쓴다"는 말은 이용 제한 위험을 낮출 뿐 없애지 않는다. 읽는 행위가 상대 화면에 흔적(읽음)을 남기는지, 어떤 권한을 새로 주는지, 코드가 무엇을 하는지를 설치 전에 한 장으로 정리해 승인받는다.

**후속(같은 날, 사용자 승인 후 설치):**
- [확인] 설치 후 목록 조회가 `chats_pane_not_observed`로 막혔다. 읽기 전용 접근성 구조 조사(문자열은 키워드만 표시)로 원인을 찾았다: 최신 맥 카톡의 채팅 탭 머리말은 정적 텍스트가 아니라 "채팅"·"오픈채팅" **버튼**이었다. 판정 함수에 버튼 조건을 더하는 로컬 패치로 해결했다(UI 동작 0회로 목록 조회).
- [확인] 목록에는 안 읽음 표시가 노출되지 않았다(숫자는 인원 수). 그래서 방을 자동으로 열지 않고 미리보기만 읽는 정책으로 정했다.
- [확인] 접근성 권한은 실행 주체(책임 프로세스) 기준이라, tmux에 주면 그 안의 에이전트 세션 전체가 화면을 조작할 수 있게 된다. 대신 **rooms 명령만 받도록 고친 사본을 컴파일해 launchd로 단독 실행**하고, 권한은 그 바이너리 하나에만 주게 했다(open 명령 거부 시험 확인).

**일반화(추가):** 접근성 같은 넓은 권한은 셸·멀티플렉서가 아니라 기능을 최소로 줄인 전용 바이너리에 준다. 오픈소스 도구가 버전 차이로 실패하면 실패 지점의 판정 조건부터 읽고, 구조 조사는 내용 대신 역할·키워드만 출력해 사생활 노출을 줄인다.

**근거:** 2026-11-24 저장소 clone과 grep 감사, README 확인, 설치 후 구조 조사·패치·rooms 전용 바이너리 시험. 정기 실행 경로의 카톡 읽기는 사용자 권한 부여 전이라 [미확인].
